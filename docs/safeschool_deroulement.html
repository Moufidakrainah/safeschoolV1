Schema de l'architecture SafeSchool
Toutes les technologies et leurs relations. Cliquez sur "Suivant" pour voir le deroulement complet.
Runtime
Node.js
Environnement qui execute JavaScript en dehors du navigateur. La base sur laquelle tout le reste fonctionne.
Framework
NestJS · Express · Vite
Structure complete qui impose une organisation et fournit des outils prets a l'emploi. Tu suis ses regles, il fait le travail repetitif.
Bibliotheque
React · Axios · bcrypt
Boite a outils que tu appelles quand tu en as besoin. Tu gardes le controle — tu decides quand et comment l'utiliser.
ORM
TypeORM
Traduit les classes TypeScript en tables SQL. Tu ecris du code objet, TypeORM genere les requetes SQL et parle a PostgreSQL.
Build Tool
Vite
Compile et sert le code frontend. Recharge automatiquement le navigateur quand tu modifies un fichier (HMR).
Conteneur
Docker
Isole chaque service dans une boite independante avec son propre environnement. Garantit que tout fonctionne de la meme facon partout.
Bloc 1 — Le Frontend C'est ce que l'utilisateur voit dans son navigateur. Il tourne sur le port 5173. Il contient trois technologies. React qui construit l'interface — les pages, les boutons, les formulaires. Vite qui compile et sert le code React au navigateur. Et Axios qui est le messager — quand l'utilisateur clique sur quelque chose, Axios envoie une requete HTTP au backend et ramene la reponse. Bloc 2 — Le Backend C'est le cerveau de l'application. Il tourne sur le port 5000. Il est construit en couches. Node.js tout en bas est l'environnement qui fait tourner JavaScript cote serveur. Express par-dessus gere le serveur HTTP — il recoit les requetes et renvoie les reponses. NestJS par-dessus Express organise tout le code en modules, gere les routes, les guards et l'injection de dependances. Passport gere l'authentification JWT — il verifie le token sur chaque requete protegee. TypeORM traduit les classes TypeScript en requetes SQL et parle a PostgreSQL. Et Winston enregistre tous les logs. Bloc 3 — La Base de donnees PostgreSQL sur le port 5433. C'est la que toutes les donnees sont stockees — les utilisateurs, les signalements, les notifications, les convocations. TypeORM parle a PostgreSQL en SQL, PostgreSQL renvoie les donnees, TypeORM les retransforme en objets TypeScript. Bloc 4 — La Stack ELK C'est le systeme de logs. Trois outils qui travaillent ensemble. Winston dans le backend envoie chaque log vers Logstash via TCP. Logstash recoit les logs, les traite et les envoie vers Elasticsearch qui les indexe et les stocke. Kibana se connecte a Elasticsearch et affiche tout ca dans un dashboard visuel sur le port 5601. Groq — en dehors des blocs C'est une API externe — elle ne tourne pas dans Docker. Quand un signalement est cree, le backend envoie la description a Groq via HTTPS. Groq analyse le texte avec le modele llama et renvoie un score et un niveau d'urgence. C'est le scoring IA. Docker — ce qui entoure tout Chaque bloc tourne dans son propre conteneur Docker isole. Docker Compose orchestre les 7 conteneurs, gere les volumes pour persister les donnees, et connecte tout le monde sur le meme reseau interne pour qu'ils puissent se parler par nom de service.

2
Construction de l'image backend
Docker exécute chaque ligne du Dockerfile du backend ligne par ligne
backend/Dockerfile
Les 7 étapes exécutées
  • FROM node:20-alpine — télécharge l'image de base Node.js 20 sur Alpine Linux
  • RUN npm install -g @nestjs/cli — installe la commande nest globalement dans l'image
  • WORKDIR /app — définit /app comme dossier de travail dans le conteneur
  • COPY package*.json ./ — copie package.json et package-lock.json en premier pour profiter du cache Docker
  • RUN npm install — installe toutes les dépendances listées dans package.json dans /app/node_modules
  • COPY . . — copie tout le code source TypeScript dans l'image
  • CMD ["npm","run","start:dev"] — commande lancée au démarrage du conteneur
Optimisation cache Docker
Si tu modifies uniquement du code TypeScript et rebuildes : Docker réutilise le cache des étapes 1 à 5 (npm install) et ne réexécute que les étapes 6 et 7. Économise 2-3 minutes à chaque rebuild.
▶
3
Montage des volumes
Docker monte les bind mounts et les volumes nommés sur chaque conteneur
docker-compose.yml
Pour le backend
  • ./backend:/app — ton dossier local écrase le contenu copié par COPY dans l'image. Tes fichiers .ts locaux sont directement dans le conteneur.
  • backend_node_modules:/app/node_modules — les dépendances installées dans l'image sont préservées dans ce volume nommé, le bind mount ne les écrase pas.
Résultat
Le conteneur voit ton code source en temps réel via le bind mount ET les node_modules installés via le volume nommé. C'est pour ça que quand tu modifies un fichier .ts sur ta machine, NestJS le voit immédiatement et redémarre.

1
PostgreSQL healthcheck passe
Le backend attend que la DB soit prête avant de démarrer
docker-compose.yml
Docker exécute toutes les 5 secondes : pg_isready -U postgres -d safeschool. Tant que ce check échoue, le conteneur backend ne démarre pas. Quand PostgreSQL est prêt, Docker lance le backend.
En parallèle, ./database/init.sql est exécuté automatiquement par PostgreSQL au tout premier démarrage — il crée les tables et insère les 12 utilisateurs de test.

main.ts s'exécute

Active le CORS pour le frontend app.enableCors({ origin: 'http://localhost:5173', methods: ['GET','POST','PATCH','DELETE'], allowedHeaders: ['Content-Type','Authorization'], }); // 3. 3
AppModule s'initialise
Module racine — connecte TypeORM à PostgreSQL et importe tous les modules
src/app.module.ts
@Module({ imports: [ // Connexion PostgreSQL via les variables .env TypeOrmModule.forRoot({ type: 'postgres', host: process.env.DB_HOST, // "database" port: +process.env.DB_PORT, // 5432 username: process.env.DB_USER, password: process.env.DB_PASSWORD, database: process.env.DB_NAME, synchronize: true, // crée/met à jour les tables automatiquement entities: [User, Report, Notification, ...], }), // Tous les modules métier AuthModule, UsersModule, ReportsModule, NotificationsModule, StudentProfilesModule, LoggerModule, ], })
synchronize: true — TypeORM compare les entités TypeScript avec les tables PostgreSQL. S'il manque une colonne ou une table, il la crée automatiquement. À désactiver en production.

Phase 3 — Les requêtes frontend
Le frontend envoie 2 types de requêtes : sans token (authentification) et avec token (les 36 autres routes protégées). Total : 38 routes.
A
Requête sans token — Authentification (2 routes)
Seules ces 2 routes sont publiques. Aucun Authorization header. C'est ici que le token est créé.
src/auth/auth.controller.ts
Routes publiques
POST /auth/login POST /auth/register
Ce que le frontend envoie
POST http://localhost:5000/auth/login Headers: Content-Type: application/json Origin: http://localhost:5173 // pas de Authorization — token pas encore créé Body: { "email": "lotfi@safeschool.com", "password": "eleve123" }
Ce que le backend renvoie
{ "access_token": "eyJhbGciOiJIUzI1NiJ9...", "user": { "id": "uuid-lotfi", "email": "lotfi@safeschool.com", "role": "student", "studentProfile": { "schoolClass": "5eme" } } }
Le frontend stocke le access_token et l'envoie dans toutes les requêtes suivantes via Authorization: Bearer <token>.

Résumé complet du cycle
De docker compose up jusqu'à la réponse — tous les fichiers impliqués
Build & Démarrage
  • Dockerfile construit l'image, installe les dépendances
  • docker-compose.yml orchestre les 7 conteneurs et les volumes
  • .env injecte les variables secrètes
  • main.ts démarre NestJS, active CORS
  • app.module.ts connecte TypeORM à PostgreSQL, charge les modules
Requête Login
  • http-logger.middleware.ts logue la requête entrante
  • auth.controller.ts route vers la bonne méthode
  • auth.service.ts cherche le user, compare bcrypt, signe JWT
  • users.service.ts requête PostgreSQL findByEmailWithProfile()
Requête Protégée (POST /reports)
  • jwt-auth.guard.ts + jwt.strategy.ts vérifient le token, injectent req.user
  • reports.controller.ts vérifie le rôle, délègue au service
  • scoring.service.ts calcule le score (5 composantes + Groq)
  • reports.service.ts sauvegarde en DB, crée notification si critique
  • logger.service.ts + logstash.transport.ts envoient les logs vers ELK
